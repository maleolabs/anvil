# Laravel Delivery Lifecycle

The Laravel standard supplies the lifecycle content within the delivery
lifecycle defined by the specification: the standard declares phases, order,
and semantics; Anvil enforces the stage model and transition rules. This
skill is the agent-facing summary of what activation runs, what rollback
reverses, and what to check.

## Activation phases (declared order)

A Laravel release activates through the standard's declared phases, in the
declared order, each run as `php artisan <command>` from the release's
working directory:

1. **`migrate`** — `php artisan migrate --force`. Migration runs AFTER the
   release is promoted to active: the release is promoted first, then the
   adapter phases execute, so a failing phase leaves the release recorded
   as active and the activation can be re-run to converge. This is the
   only reversible activation phase (rollback: `php artisan
   migrate:rollback`).
2. **`config_cache`** — `php artisan config:cache`. **Irreversible**: a
   rollback cannot restore the previous release's caches — the previous
   release's own activation regenerates them from its code.
3. **`route_cache`** — `php artisan route:cache`. **Irreversible** (same
   semantics).
4. **`event_cache`** — `php artisan event:cache`. **Irreversible** (same
   semantics).

There is no queue-restart phase in the standard's activation table, and
`view:cache` is deliberately absent from activation (it is not reversible,
so it exists only as a build phase).

## Failure semantics

- Every phase reports a structured outcome through the activation contract;
  the JSON result is authoritative for the phase outcome.
- A failing phase fails the activation command with an error. Because the
  release is promoted to active before the phases run, re-running
  activation re-executes the phases from the start to converge.
- The irreversible cache phases report an informational result on rollback
  and never block it.

## Rollback semantics

- Rollback restores the previously active release. `migrate` is reversed
  by `php artisan migrate:rollback`.
- The cache phases are irreversible: rollback proceeds and reports them
  as informational — their effects are regenerated by the previous
  release's own activation, never "un-run".
- Irreversibility never blocks rollback.

## Adoption

- Register the standard: `anvil standard install anvil-standard-laravel
  <version>`. Adoption pins the version; release metadata, trust anchors,
  and the declared capability are validated at adoption.
- Activate a release on a server runtime: `anvil deployment activate
  <project-id> <release-id>` (target-centric, both arguments required) or
  `anvil server release activate <project-id> <release-id>`
  (project-centric) — the two styles are aliases for the same operation.
- Roll back: `anvil deployment rollback <project-id>` or `anvil server
  release rollback <project-id>`.
- Check lifecycle state and evidence: `anvil status` / `anvil project
  status` and the verification report record what ran and what passed.

## Verification

- The standard declares eight structural verification checks (artifact
  presence): `vendor_present`, `bootstrap_structure`, `config_files`,
  `artisan_file`, `composer_json`, `env_file`, `app_directory`,
  `routes_directory`. They run during artifact verification and are
  mandatory: a failed check blocks acceptance. Never bypass a check to
  "get the release out".

## When to use this skill

- Planning or executing a Laravel release activation or rollback under Anvil.
- Diagnosing why an activation failed or what a rollback will and will not
  undo.
- Reviewing whether a Laravel project's release flow matches the standard's
  declared lifecycle.

For project conventions — scaffold, build, config surface, verification
expectations — load `laravel-conventions`.
