# Limitations and Deferrals

Everything below is **verified current behavior**. Each item states what works today and what is coming. When a limitation is lifted, update the corresponding page and remove the entry here.

> **Vocabulary (ADR-032):** `anvil adapter ...` command names in this document are the **deprecated v1.x command surface** of the canonical `standard` commands (ADR-032): retained as aliases until the window closes (ADR-028). `adapter list`/`inspect`/`install` map to (mirror) the corresponding `standard` commands — they are not functional aliases (`adapter list` was the v1.x closed-set PATH discovery; `standard list` is the registry-driven index surface) — `adapter use` maps to `anvil init --framework <name>`, and `adapter uninstall` has no standard-named replacement. Migration paths for existing users and CI workflows: [docs/migration-guide-v2.md](../docs/migration-guide-v2.md).

## 1. Delivery lifecycle standard binary distribution

- **Status:** resolved (TS-007-034 — TS-007-037); distribution source changed by the repository split (ADR-025); switch-over complete (TS-016-04-01)
- **Works today:** standard binaries are built and released from their own standard repositories — [anvil-standard-laravel](https://github.com/maleolabs/anvil-standard-laravel) and [anvil-standard-flutter](https://github.com/maleolabs/anvil-standard-flutter) (TS-016-01-01, TS-016-02-01; ADR-025 §6.2) — never from Core: Core CI and the Core release pipeline contain no standard build/publish steps, and Core release assets carry runtime artifacts only (TS-016-03-03, ADR-025 §3.5, §4.7). Since the installer/discovery switch-over (TS-016-04-01), the binaries are distributed as release assets `anvil-adapter-<framework>-{os}-{arch}` (linux/darwin × amd64/arm64) of the **standard repositories' releases** — the registry distribution channel (ADR-030) — and install as `anvil-adapter-<framework>` next to the CLI (the executable-resolution contract, ADR-025 decision 4):
  - `install.sh --with-adapters <name[,name...]>` — installs standard executables alongside the CLI from the standard repositories' latest releases, verified against the attestation-bound digest declared in each release's signed metadata (pinned key; `SHA256SUMS.txt` remains as a fallback check) (whitelist: `laravel`, `flutter` only; missing checksums abort the install — fail-closed)
  - `anvil standard install <id> <version>` — the explicit registry flow: resolves `anvil-standard-<id>` from the static registry index (recorded version, or the highest adoptable version), runs the full adoption validation (strict parse, lifecycle + compatibility, release content integrity, publisher attestation, out-of-band trust anchors — ADR-022; no first-use acceptance), records the installed standard, and installs the binary from the same release; the deprecated v1.x alias `anvil adapter install <name>` maps to this flow (`--force` / `--json` supported on the alias, ADR-032)
  - `anvil standard list` — the registry-driven view of the standards offered for adoption in the registry index; the deprecated v1.x `anvil adapter list --available` (ADR-032) is the adapter view of the same index
  - `anvil adapter uninstall <name>` (deprecated v1.x; no standard-named replacement — ADR-032) — unchanged
  - `anvil update` — refreshes installed standards to the release version of their RECORDED standard (TS-016-04-01): the sync resolves each standard's release channel from its installed-standard record (the post-split distribution path, ADR-025 §3.5 / ADR-030) and honors the recorded version pin — it never bumps versions and never fetches from a Core release; standards without a recorded standard record are skipped with a hint pointing at the registry adoption command (`anvil standard install <id> <version>` — idempotent re-validation; the deprecated alias `anvil adapter install <name> --force` also works during the window) (refresh-only, never installs new ones)
- **Dual-run window (ADR-028):** the v1.x closed-set PATH/CLI-dir discovery behind `adapter list`/`inspect`/`use` was **removed at the switch-over gate** (TS-017-02-02): post-gate, discovery is registry-only — `standard list` installed-view entries come from the installed-standard records, not from PATH scanning (migration-guide-v2 §5.3). The `adapter` vocabulary commands remain registered aliases of the `standard` surface until the aliases are removed at window end (ADR-032; [deprecation schedule §4.1](../docs/planning/ANVIL_V2_DEPRECATION_SCHEDULE.md)).
- **Previously:** `install.sh` and release builds shipped only the `anvil` binary, so a fresh server failed with `adapter executable "anvil-adapter-laravel" not found on PATH` and the workaround was a manual `go build` per machine. Manual builds remain an option for development only — see the [Laravel standard repository](https://github.com/maleolabs/anvil-standard-laravel) and the [Flutter standard repository](https://github.com/maleolabs/anvil-standard-flutter) (TS-016-01-01, TS-016-02-01). Before TS-016-04-01, `install.sh --with-adapters` and `anvil adapter install` downloaded the binaries from the **Core** GitHub release; the switch-over moved them to the standard repositories' releases (registry-based resolution).

## 2. Manifest command metadata in packaged artifacts

- **Status:** resolved (CH-012-001)
- **Works today:** `anvil artifact package` pulls `activation_commands` / `rollback_commands` from the standard's manifest command when the project declares a framework and the standard's executable is installed (005-adapter-command-contract §10.10, ADR-009 §8.1, ADR-017 — v1.x references; the command contract is part of the delivery lifecycle specification). The standard is optional (ADR-009 §9.7) — a missing or failing standard degrades to a warning and artifacts ship without command metadata (`omitempty`, backward compatible). The Laravel values are defined (`php artisan migrate --force` etc. — see [manifest.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/manifest.md))
- **Previously:** packaging never pulled the Laravel values from the standard — packaged artifacts contained no command metadata

## 3. `framework.laravel.*` config keys are inert

- **Status:** reserved, not yet effective
- **Works today:** the keys are declared (namespace `framework.laravel.`) and validated (SemVer, cache driver list, relative-path, safe-flags rules) by the standard's `validate` command — the standard owns its value rules (C6). Since TS-015-03-01, `anvil init --framework laravel` WRITES a `framework.laravel:` section into `anvil.yaml` when the installed standard's record carries configuration extension content (keys with declared defaults only; see [init.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/init.md)) — practically absent for Laravel today because no `anvil-standard-laravel` installed-record content exists yet — the standard source repository now declares the config extension (TS-016-01-01), but the supplier side (embedding content into the installed-standard record at install/update) is EPIC-016/EPIC-018 scope (item 6). Since TS-015-03-02, the runtime validates the framework section against the installed standard's declared config extension rules (`anvil config validate` and the config command family): required declarations are enforced and values must be strings — no hardcoded framework rules exist in the runtime (ADR-026 decision 2); see [config.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/config.md)
- **Does not work:** no build/activation flow consumes the keys yet (no `framework.laravel:` section is written when the standard supplies no content, and nothing reads the values at runtime)
- **Coming:** consumption by build and activation flows + standard-supplied `framework.laravel:` defaults (standard content extraction, item 6)
- See [config.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/config.md) for the full key table

## 4. No Core-hosted usage guide for `anvil init --framework flutter`

- **Status:** implemented, documentation pending
- **Works today:** `anvil init my-app --framework flutter` is implemented and generates a platform-aware build template (web / apk / ios targets via `metadata.platforms` / `metadata.target`); `anvil init my-app --framework laravel` (implemented); `anvil init my-app` (plain, no framework)
- **Does not work:** there is no Core-hosted usage guide for the Flutter standard — the v1.x plan for a `wiki/adapters/flutter/` usage guide is historical: usage documentation for a standard is owned by the standard's repository
- **Note:** the Flutter standard executable is distributed — install it with `install.sh --with-adapters flutter` or `anvil standard install anvil-standard-flutter <version>` (the deprecated v1.x alias `anvil adapter install flutter` remains during the window, ADR-032 — see the vocabulary note above) (see item 1)
- **Coming:** Flutter usage documentation in the Flutter standard's repository (templates, verification, deployment model)

## 5. `anvil artifact verify` and framework verification checks

- **Status:** resolved (CH-012-001)
- **Works today:** `anvil artifact verify <path>` runs the generic integrity checks (archive validity, manifest presence/content, checksum match) and then the standard-declared framework verification checks when the project declares a framework and the standard's executable is installed (005-adapter-command-contract §4, TS-P7-11; `runFrameworkVerification`). The standard is optional (ADR-009 §9.7) — a missing standard degrades to a warning and only the generic checks run; a present but failing standard fails the verification
- **Previously:** the 8 Laravel verification checks ran only at server install time — there was no CLI command to run them against an artifact locally
- See [verify.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/verify.md)

## 6. `vendor/` inclusion for framework projects is standard-driven (interim gap)

- **Status:** open — the Core owns no framework-specific artifact defaults (TS-015-01-03, ADR-026 decision 1); framework config key resolution is implemented (TS-015-03-01), but no mechanism that can touch the Core-owned `artifact.exclude` default exists yet, so `vendor/` stays excluded for Laravel projects
- **Works today:**
  - `anvil init` writes framework-agnostic compiled defaults for every project. The compiled `artifact.exclude` default strips `vendor/**` and `node_modules/**`; the previous Core-owned Laravel adjustment (exclude list minus `vendor/**`, so vendor/ stayed packaged — ADR-017) is removed
  - **Config key resolution** — when the installed standard's record carries configuration extension content (EPIC-013 contract: namespace + keys with description/default/required), `anvil init --framework <name>` resolves it and merges the declared keys and their defaults into `anvil.yaml` under the framework's own namespace (`framework.<name>.<key> = default`, e.g. `framework.laravel.version: 11.0.0`) — the defaults come from the installed standard, never from the runtime (ADR-026 decision 2). A resolved standard that declares no config extension content is a valid state: init succeeds with an explicit warning and no framework config section (a standard may declare nothing in a category). Framework declarations without an installed standard HARD-FAIL (TS-015-02-02)
  - **Config validation from the standard** — `anvil config validate` (and the config command family: get/list/levels) enforces the installed standard's declared config extension rules on the framework section (TS-015-03-02, ADR-026 decision 2): required declarations are enforced and values must be strings (the contract extends no other value type). Errors identify the offending fully-qualified key (`framework.<name>.<key>`) and the expected format; a declared framework without an installed standard HARD-FAILS the whole config family with the install remediation (ADR-026 decision 3 — deliberate, never a silent pass-through). A standard without content supplies no rules — the framework section passes through. The enforcement surface is the config family only: other load-config consumers (artifact packaging, server release, pipeline flows) do not enforce framework rules — deliberate, since the framework section is not effective until consumption lands (item 3); ratified TS-015-03-02 §6.7
- **Why the gap is NOT closed by config extension or template content:** configuration extension content carries framework-namespaced config keys only (`framework.<name>.*`, namespace-isolated per the EPIC-013 contract), and template content (TS-015-02-03) supplies pipeline files only — neither maps onto the Core-owned `artifact.exclude` key, so a standard's content cannot change what the artifact filter strips. Closing the `vendor/` gap needs a mechanism that can supply or adjust Core artifact defaults — standard content extraction is EPIC-016/EPIC-018 scope
- **Does not work (interim):** a Laravel project initialized after TS-015-01-03 packages without `vendor/`; the server install `vendor_present` check then fails. To restore `vendor/` today, override `artifact.exclude` in `anvil.yaml` with the compiled defaults minus `vendor/**` (see [verify.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/verify.md))
- **Fixture limitation:** no `anvil-standard-laravel` config extension or template content exists in the specification corpus yet (the EPIC-013 command-contract fixtures are `rails`-namespace declarations; the standard repositories are EPIC-016/EPIC-018 scope). The resolution, generation, and validation are generic — any installed standard whose record carries content resolves, generates, and validates from it (TS-015-02-03, TS-015-03-02, see [init.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/init.md)) — and the supplier side (embedding config extension / template content into the installed-standard record at install/update) is not implemented yet (EPIC-013/EPIC-016/EPIC-018 scope; see TS-015-03-01 §6.5, TS-015-02-03 §6.5 and TS-015-03-02 §6.5)
- **Coming:** standard content extraction (EPIC-016/EPIC-018) as the mechanism for artifact defaults
- See [init.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/init.md)

## 7. Local `anvil pipeline build` does not invoke the standard executable

- **Status:** partially resolved — server release builds run through the standard executable; local pipeline builds stay in the generic engine
- **Works today:** `anvil server release build <project-id>` runs the project's framework standard `build` command — the standard-owned build phases are the single source of build knowledge at server release time (ADR-020 §4), the 15-minute timeout bound is enforced, and `--target`/`--strict` are supported (TS-007-040, TS-007-041); `anvil pipeline build` executes `.anvil/pipelines/build.yaml` directly (the Laravel template generated at init)
- **Does not work:** local `anvil pipeline build` still executes the pipeline YAML via the generic engine instead of dispatching to the standard executable (ADR-020 §3 — v1.x adapter terminology; the dispatch target is the standard implementing the command contract) — the local template and the standard's build phases can still drift
- **Coming:** optional dispatch of local builds to the standard executable (ADR-020 §3)
- See [build.md](https://github.com/maleolabs/anvil-standard-laravel/blob/main/docs/build.md)

## 8. Framework knowledge lives in delivery lifecycle standards (removed from Core)

- **Status:** resolved — framework knowledge (pipeline templates, build phases, discovery, config defaults, the framework whitelist) is removed from the Core (TS-015-01-01, TS-015-01-02, TS-015-01-03, ADR-026 decision 1); the Core import graph provably contains zero framework packages (`bash scripts/framework-free-check.sh`, ADR-026 §3 decision 4). Adding a framework means authoring a delivery lifecycle standard, with no Core release required for discovery, template generation, or server builds.
- **Works today (TS-007-038..041, TS-015-01-01..03, TS-015-02-01..03, TS-015-03-01..02):**
  - **Standard-driven templates** — `anvil init --framework <f>` generates `.anvil/pipelines/build.yaml` / `ci.yaml` from the installed standard's template content when the resolved standard's record carries it (TS-015-02-03, ADR-026 decision 2): each declared template is validated through the pipeline loader before any filesystem work (a broken template fails init BEFORE any project file is created, with the reinstall remediation — no partial generation) and written as the standard supplies it. A standard that declares no template content is a valid state (command-contract §4.1): generation warns explicitly and falls back to the interim standard-driven path — the installed standard's `template` command supplies the definitions (ADR-020), validated through the pipeline loader. The Core-embedded template functions and the `NewFrameworkProjectConfig` switch are removed.
  - **Registry-driven discovery** — post-switch-over (TS-017-02-02), discovery is registry-only: `anvil standard list`/`inspect` read the installed-standard records and the registry index; an executable that was never adopted is not discovered (migration-guide-v2 §5.3). The executable-resolution contract keeps the v1.x naming (`anvil-adapter-<name>`, ADR-025 decision 4); the deprecated v1.x `adapter list`/`inspect`/`use` aliases remain registered until window end (ADR-032).
  - **Server build wiring** — `anvil server release build <project-id>` executes the project standard's build phases (15-minute bound, first-failing-phase semantics, `--target`/`--strict` parity) — the standard-owned phases are the single source of build knowledge at release time.
  - **Declaration pass-through** — `anvil init --framework <f>` stores the declaration in `anvil.yaml` without Core-side whitelist validation (no "unknown framework" rejection); the declaration requires the installed delivery lifecycle standard to pass the standard-missing hard-fail (TS-015-02-02) — framework config keys, defaults, and template content come from the installed standard (TS-015-03-01, TS-015-02-03)
  - **Framework-standard resolution** — `anvil init --framework <f>` resolves the declared framework to the installed delivery lifecycle standard through the installed-standard records (TS-015-02-01, ADR-026 decision 2): `laravel` → `anvil-standard-laravel` (ADR-021 §3.1); the success message reports the resolved standard and pinned version. No-match cases HARD-FAIL initialization with actionable remediation (TS-015-02-02, ADR-026 decision 3): an explicit declaration with no installed standard fails with the install command (`anvil standard install anvil-standard-<f> <version>`), no project files are created, and there is no graceful fallback to a generic lifecycle — silent degradation was explicitly rejected (§4)
  - **Config key resolution from the standard** — when the resolved standard's record carries configuration extension content, `anvil init --framework <f>` merges the declared keys and their defaults into `anvil.yaml` under `framework.<name>.*` (TS-015-03-01, ADR-026 decision 2); a resolved standard without content warns explicitly and merges nothing — see item 6
  - **Config validation from the standard** — the runtime enforces the installed standard's declared config extension rules on the framework section (`anvil config validate` and the config command family, TS-015-03-02, ADR-026 decision 2): required declarations enforced, values must be strings, errors identify the offending fully-qualified key and the expected format; a declared framework without an installed standard hard-fails with the install remediation (ADR-026 decision 3) — no hardcoded framework validation rules exist in the runtime
- **Does not work:** local `anvil pipeline build` still executes `.anvil/pipelines/build.yaml` via the generic engine instead of dispatching to the standard executable — optional dispatch is deferred (ADR-020 §3, see item 7) — see item 6 for the interim `vendor/` gap; the install/update flows do not yet embed template content into the installed-standard record (supplier side — the standard-driven generation path is reachable only through records that already carry content, EPIC-016/EPIC-018 scope, see TS-015-02-03 §6.5)
- **Coming:** optional dispatch of local builds to the standard executable (ADR-020 §3); standard content extraction into installed-standard records at install/update (EPIC-016/EPIC-018)
- See [ADR-020](../docs/decisions/020-adapter-owned-pipeline-templates-and-discovery.md)

## 9. `anvil standard list`/`inspect` registry-driven discovery

- **Status:** canonical (the v1.x closed-set discovery was removed at the switch-over gate, TS-017-02-02)
- **Works today:** `anvil standard list` and `anvil standard inspect` (with `--index`, `ANVIL_REGISTRY_INDEX`, default `<config>/anvil/registry`) list and inspect delivery lifecycle standards from a static registry index; retired releases are not offered for fresh adoption; deprecated releases show a warning and removal date; invalid entries are marked, not dropped
- **Does not work / limits:** index freshness depends on updating the local index; discovery output for a missing index is a not-found error (exit 3)
- **How to provision:** the index resolves in order `--index <path>` → `ANVIL_REGISTRY_INDEX` → the default `<user config dir>/anvil/registry`. The index is published in the standard repositories' releases — the registry distribution channel (ADR-030); [migration-guide-v2 §5.4.1](../docs/migration-guide-v2.md) has the setup
- **Coming:** full documentation alignment completion (EPIC-020)
- **Note:** `anvil adapter list` (deprecated v1.x surface, ADR-032) remains registered as an alias during the dual-run window

## 10. Registry-driven standard adoption: online install and offline bundle install

- **Status:** canonical (the deprecated v1.x adapter commands remain registered aliases during the window)
- **Works today:** registry-driven standard adoption has two install surfaces plus the update flow: `anvil standard install <id> <version>` installs from the static registry index (strict parse, lifecycle gate, compatibility, trust verification against the operator's anchor allowlist, recorded resolution kind `distribution`); `anvil standard install-bundle <bundle-path>` installs from bundled install material with **no network access** — the same validation path (compatibility + trust), recorded resolution kind `bundle`; version changes are handled by the update flow (TS-014-03-02). Both installs are idempotent by identity plus version: re-installing the same version re-validates and refreshes the record, including the recorded resolution source (last adoption wins); deprecated releases install with a warning; retired releases are not offered for fresh adoption
- **Does not work / limits:** there is no offline update path — installing a different version of an already-installed standard from a bundle is rejected with guidance to use the update flow, which is online-only in this sprint. Trust anchors always come from the operator host (`--trust-anchors` / `ANVIL_TRUST_ANCHORS` / default `<config>/anvil/trust-anchors.json`), never from the bundle — a missing or invalid anchor allowlist fails the install closed
- **Note:** `anvil adapter list` and the adapter command surface (deprecated v1.x, ADR-032) remain registered as aliases during the dual-run window
